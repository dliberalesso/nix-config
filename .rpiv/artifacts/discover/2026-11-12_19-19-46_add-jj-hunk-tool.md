# FRD: Add jj-hunk-tool package

## Summary

Add the upstream `jj-hunk-tool` Rust CLI as a reproducible, immutable-revision Nix package with both flake and overlay outputs. Install it globally for Home Manager users, rely on the caller's Jujutsu installation, and add the upstream-style `jj hunk` alias to the existing Jujutsu configuration.

## Problem & Intent

When asked, "What problem are you solving by adding jj-hunk-tool, and who will use it?", the developer answered: **"All of the above."** This referred to the three presented audiences: an interactive developer improving manual Jujutsu workflows, a configuration maintainer making the tool reproducibly available across machines, and an automation operator using it in non-interactive workflows.

The runtime intent was finally clarified in the developer's own words: **"The package should not provide it's own jj."** This supersedes the earlier Lazymoji-style runtime-dependency answer.

## Goals

- Package non-interactive, hunk-level Jujutsu operations for interactive, configuration-management, and automation use.
- Make one pinned derivation available through `nix build .#jj-hunk-tool`, `nix run .#jj-hunk-tool`, and `pkgs.jj-hunk-tool`.
- Install `jj-hunk-tool` on the default Home Manager user PATH on all configured hosts.
- Use the caller's `jj` executable for direct, `nix run`, and `jj hunk` invocations rather than bundling another Jujutsu version.

## Non-Goals

- Supplying or wrapping the package with its own Jujutsu executable.
- Creating a new opt-in host profile or making host-specific package selections.
- Tracking a mutable `main` reference or adding a dedicated flake input for this package.
- Requiring runtime smoke tests, the upstream test suite, or repository-wide `just lint` as completion checks; the selected validation scope is build-only.

## Functional Requirements

1. The flake SHALL build `mvzink/jj-hunk-tool` as the package and main program `jj-hunk-tool` using its upstream Rust sources and lockfile.
2. The package SHALL fetch an immutable upstream commit with fixed source and Cargo dependency hashes; upstream currently has no tags or releases and declares Cargo version `0.1.0`.
3. The package SHALL be exported as both `packages.<system>.jj-hunk-tool` and `overlayAttrs.jj-hunk-tool`, enabling direct flake commands and `pkgs.jj-hunk-tool` references.
4. The package SHALL be installed through global `unify.home`, placing `jj-hunk-tool` on every configured Home Manager user's PATH.
5. The packaged command SHALL remain unwrapped and resolve `jj` from the caller's PATH; operations that invoke Jujutsu require the caller to have it installed.
6. The existing Home Manager Jujutsu configuration SHALL define a `hunk` alias through its established `utilExecFor` pattern, making `jj hunk ...` invoke the packaged tool.

## Non-Functional Requirements

- **Performance**: No specific latency, throughput, or load constraint beyond using the upstream compiled Rust binary.
- **Security**: Pin source and dependency content with immutable revisions and hashes; introduce no service, credential handling, or privileged system integration.
- **UX / Accessibility**: Support both the direct `jj-hunk-tool`/standalone `nix run` interface and the shorter `jj hunk` command while consistently using the caller's active Jujutsu installation.
- **Reliability**: Rebuild the same pinned source reproducibly and require a successful package build. Runtime smoke checks and upstream tests are not required by the selected validation scope.

## Constraints & Assumptions

- Use a self-contained, auto-discovered `modules/packages/jj-hunk-tool.nix` module for the derivation, exports, and global installation.
- Follow the package layer's dual-export contract without adding a runtime wrapper or bundled Jujutsu dependency.
- Modify `modules/programs/jujutsu.nix` only for the `jj hunk` alias; package installation remains in the package module.
- Research must determine the current immutable upstream revision, appropriate unstable version label, source hash, and Cargo dependency hash.
- The caller's `jj hunk` workflow already receives Jujutsu through global `programs.jujutsu.enable`; direct and `nix run` invocations outside that environment must supply `jj` on their own PATH.
- Completion validation is limited to `nix build .#jj-hunk-tool` by explicit developer choice.

## Acceptance Criteria

- [ ] Running `nix build .#jj-hunk-tool` exits successfully and produces an executable at `result/bin/jj-hunk-tool`.

## Recommended Approach

Add a self-contained `modules/packages/jj-hunk-tool.nix` using the conventional Nixpkgs Rust builder, pinned to an immutable commit and dual-exported through `packages` and `overlayAttrs`; install the unwrapped command through global `unify.home` so it uses `jj` from the caller's PATH. Add one `hunk = utilExecFor pkgs.jj-hunk-tool;` alias in `modules/programs/jujutsu.nix`, with no new profile or flake input.

## Decisions

### Dual package exports

**Question**: Pre-resolved from codebase evidence — "From the probe I inferred that reusable custom packages are exported through both `packages.<name>` (for `nix build`/`nix run`) and `overlayAttrs.<name>` (for `pkgs.<name>`), following `.rpiv/guidance/modules/packages/architecture.md:26-55` and `modules/packages/zennotes-tui.nix:8-12`. Keep this for jj-hunk-tool, or change it?"
**Recommended**: Keep dual exports.
**Chosen**: Keep dual exports.
**Rationale**: Evidence: `.rpiv/guidance/modules/packages/architecture.md:70` and `modules/packages/zennotes-tui.nix:8-12`; confirmed because all three intended usage modes can share the same derivation.

### Global user installation

**Question**: "Should jj-hunk-tool merely be buildable through the flake, or also be installed on users’ PATH? Package exports alone do not install it (`modules/packages/defuddle.nix:39-46` shows the separate `home.packages` step)."
**Recommended**: Install for all users.
**Chosen**: Install for all users through global `unify.home`.
**Rationale**: Matches the stated interactive, configuration, and automation intent without requiring new host profile selections.

### Self-contained package module

**Question**: "Where should the Home Manager installation live relative to the new derivation?"
**Recommended**: Keep derivation, dual exports, and global installation in `modules/packages/jj-hunk-tool.nix`.
**Chosen**: Self-contained package module.
**Rationale**: Optimizes package cohesion and follows `modules/packages/defuddle.nix:1-46`, while accepting separation from the other Jujutsu helpers.

### Immutable source pin

**Question**: "Upstream has no tags or releases and declares version `0.1.0` in Cargo.toml. How should the Nix package select its source?"
**Recommended**: Pin an exact immutable commit with a fixed hash.
**Chosen**: Pin exact commit.
**Rationale**: Optimizes reproducible builds despite absent upstream releases, with manual revision bumps accepted as the update cost.

### Jujutsu command alias

**Question**: "Beyond installing the `jj-hunk-tool` binary, should this add upstream’s suggested `jj hunk` command alias? Existing Jujutsu aliases use `utilExecFor` in `modules/programs/jujutsu.nix:46-78`."
**Recommended**: Add the `jj hunk` alias.
**Chosen**: Add `jj hunk` through the existing alias pattern.
**Rationale**: Matches upstream's interactive usage and the repository's established Jujutsu ergonomics for a small additional configuration change.

### Caller-provided runtime Jujutsu

**Question**: "Should the exported command use `jj` from the caller’s PATH, or wrap it with this flake’s Jujutsu package?"
**Recommended**: Use the caller's PATH and require Jujutsu separately.
**Chosen**: The package should not provide its own `jj`; use the caller's PATH. This supersedes the earlier Lazymoji-style runtime-dependency answer.
**Rationale**: Keeps the upstream binary unwrapped and consistently respects the caller's active Jujutsu installation; configured Home Manager hosts already enable Jujutsu at `modules/programs/jujutsu.nix:61-65`.

### Build-only completion validation

**Question**: "Which checks should define done for this package?"
**Recommended**: Full package checks: formatting, build with upstream tests, `--help` and no-external-Jujutsu smoke tests, and `just lint`.
**Chosen**: Build only.
**Rationale**: The developer explicitly prioritized minimal validation effort over runtime, upstream-test, and repository-wide integration coverage.
